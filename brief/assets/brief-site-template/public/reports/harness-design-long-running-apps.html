面向长运行应用的 Harness 架构

Anthropic 的这篇工程文章表面上讨论 harness，真正的问题是：当一个 Agent 连续工作数小时之后，谁来定义目标、谁来判断质量、谁来决定它该继续还是返工。

基于：Harness design for long-running application development Anthropic / Prithvi Rajasekaran 2026-03-24

长运行应用开发不缺“能继续写代码”的模型，缺的是持续判断系统。planner、generator、evaluator 的价值，不在于多代理这个形式，而在于把目标设定、生产执行和质量审查从同一个模型自我循环里拆开。

这篇文章的起点很实际：作者想让 Claude 做两件事，一是产出更好的前端设计，二是在较少人工介入下构建完整应用。早期提示词和 harness 已经能显著改善基线，但很快遇到两个上限：主观质量难以稳定提升，长时间自主开发容易偏航。

解决方案不是简单延长上下文，也不是把更多 agent 堆在一起。文章最有价值的部分，是把“工作”和“判断”拆开。生成者负责做，评价者负责挑错；规划者负责把一句模糊的需求扩展成产品规格，但不把实现路径写死。这种结构让系统不再依赖同一个模型对自己的作品给出乐观评价。

自评是长运行 Agent 的薄弱环节

文章先从前端设计实验切入，这不是偶然。设计质量很难用单个测试断言验证，正好暴露了模型自评的问题。作者观察到，当模型评价自己的输出时，会倾向于说服自己“已经不错”，即使人类观察者能明显看出界面平庸、模板化或缺少原创性。

解决方式是建立一个独立 evaluator，并把审美判断拆成四个可评分维度：design quality、originality、craft、functionality。这里的重点不是把审美完全量化，而是给模型一个可执行的批评语言。没有这个语言，generator 只能在“更好看一点”的模糊反馈里打转。

这组标准反过来塑造生成结果。作者提到，criteria 里的措辞会把输出带向特定方向；例如强调“museum quality”会让设计呈现某种风格收敛。换句话说，rubric 不是评审结束后才出现的表格，它本身就是生成系统的一部分。

真正的 harness 是质量系统，不是执行脚本

把这个思路迁移到完整应用开发后，三代理结构变得更清晰：planner 负责规格，generator 负责实现，evaluator 负责验收。早期版本还要求 generator 和 evaluator 在每个 sprint 前协商 sprint contract，先确定“本轮做到什么才算完成”，再开始写代码。

这种合同机制不是为了形式化流程，而是为了避免长运行任务里最常见的漂移：开始时目标太模糊，中途实现越写越远，最后模型又用自己的解释批准自己的输出。文件通信、git、Playwright MCP 和评分标准共同组成了一个质量回路。

成本划出了适用边界

文章里的两个实验都没有回避成本。2D retro game maker 的 solo run 约 20 分钟、9 美元；full harness 约 6 小时、200 美元。后者贵得多，但差异也很直接：solo run 的核心游戏玩法没有真正连上，full harness 至少生成了可玩的 game maker，并包含 sprite editor、AI 辅助、行为模板、分享等更完整功能。

evaluator 的价值也体现在 bug 粒度上。它不是简单说“还不错”或“不够好”，而是能指出矩形填充工具没有触发 fillRectangle、删除实体条件写错、FastAPI route 顺序导致 reorder 被当作 frame_id 解析等具体问题。这样的反馈能直接返回 generator 修复。

高成本 harness 适合高价值任务。它不是日常小改动的默认选择，而是当任务复杂度超过单模型稳定边界时，用成本换质量的一种工程安排。

模型变强后，harness 要变薄

文章后半部分的重要性在于，它没有把三代理结构神化。作者明确提出，每个 harness 组件都代表一种关于模型短板的假设；这些假设会随模型变强而过期。Opus 4.6 发布后，作者开始删除组件，而不是继续叠加控制。

Harness 的承重变化 Model Capability Shift
Earlier

多上下文交接：早期长运行 harness 依赖 initializer、feature list、progress file 和 git，让新 session 能接续工作。

Opus 4.5

需要 sprint 分解：模型存在 context anxiety，sprint contract 帮助它分块推进并保持任务边界。

Opus 4.6

移除 sprint construct：更强模型可以连续构建更长时间，evaluator 变成末端检查和多轮修复。

浏览器 DAW 实验说明了这种变化。更新后的 harness 仍然昂贵，约 3 小时 50 分钟、124.70 美元，但 builder 第一轮连续运行 2 小时 7 分钟，已经不需要 Opus 4.5 时那种强制 sprint decomposition。QA 仍有价值：它发现很多核心 DAW 功能只是 display-only，录音还是 stub，clip resize、split、EQ 曲线等交互不完整。

这篇文章改变的是 harness 的定义

如果只把 harness 理解为“让 Agent 连续跑起来的外壳”，就会错过这篇文章的重点。它真正展示的是一套持续校准系统：规格如何形成，生成如何推进，评价如何约束，模型升级后哪些控制可以移除。

这也解释了为什么作者最后没有给出固定模板。随着模型提升，脚手架会变薄；但更强模型也会让更复杂的 harness 组合变得有意义。空间不会缩小，而是移动。AI 工程的工作不是找到一次性的最佳结构，而是持续发现当前模型能力边界之外，仍然值得用系统设计去补足的那部分。
